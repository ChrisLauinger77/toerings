# Reliability changes and validation

The current repository is the product baseline. These changes preserve the existing CPU normalization, temperature aggregation, observed-process disk throughput, interface inclusion, four-disk limit, optional-feature policy, and multiple-instance behavior. The approved UX changes are scrolling below 850 logical pixels, thinner rings for large CPU counts, and the memory label “Total.”

## Runtime ownership

`Sampler` owns one worker thread, which constructs and exclusively uses `DataCollector` and its mutable baselines. It publishes complete snapshots through a short mutex critical section. The IPC command clones that snapshot; platform collection never runs in the IPC handler. Sequence, age, and failure fields distinguish startup, stale data, and new samples. Age starts at sampler creation until the first successful sample, so blocked initialization or first collection becomes stale after five seconds too. A successful publication resets age and clears the stale state. A collector panic discards the collector and retries with fresh baselines.

The Svelte mount owns polling, native listeners, window operations, and external-IP refresh. Polling permits one outstanding request and retries after invocation or processing failures. Unavailable sources produce empty widget inputs and graph gaps. Each chart action destroys its uPlot instance on teardown. Preferences remain in the existing localStorage keys; geometry persists the main panel's anchor independently of which side contains preferences.

## Current automated validation baseline

The current repository passes the local checks that do not require another operating system or an interactive desktop:

- `npm run check`: zero errors and warnings.
- `npm run lint`: passes.
- `npm test`: all 28 frontend and release tests pass.
- `npm run build`: passes.
- `cargo test --locked --manifest-path src-tauri/Cargo.toml`: all 33 Rust tests pass on Linux.

The merged reliability and maintenance PRs [#77](https://github.com/ChrisLauinger77/toerings/pull/77) through [#82](https://github.com/ChrisLauinger77/toerings/pull/82) passed the established CI matrix: Ubuntu 22.04 x86_64, macOS arm64, macOS Universal, and Windows x64. Each matrix job performs a clean `npm ci`, the frontend checks/tests/build, locked Rust tests, and a locked Tauri build. Linux additionally repacks and inspects the Debian, RPM, and AppImage bundles and smoke-tests the Debian and AppImage under Xvfb. macOS verifies the strict ad-hoc app signature, and Windows performs a ten-second executable startup smoke test and creates the NSIS and portable bundles.

These checks establish compilation, unit/regression behavior, package structure, signatures where configured, and limited startup survival. They do not claim interactive GUI behavior, native menu appearance, compositor-specific behavior, suspend/resume recovery, or long-running telemetry correctness.

## Linux X11 startup follow-up

[CI on commit `9b3cff9`](https://github.com/ChrisLauinger77/toerings/actions/runs/34013167944) passed native tests on every platform but the installed Debian package aborted under Xvfb with an XCB threading assertion. Startup now calls `XInitThreads` before Tauri/GTK initialization and worker creation, checking its return value. The Linux dependency uses the same `x11` version already present in the Cargo lockfile. This initializes Xlib locking without selecting a graphics backend or opening a display.

The Debian and AppImage smoke tests preload `tests/native/x11-thread-guard.c` to reject `XOpenDisplay` before successful thread initialization, and require an explicit verification marker as well as the existing ten-second survival check. The guard only monitors the `ToeRings` executable; inherited use in WebKit subprocesses is ignored. Local controlled probes covered missing, failed, and successful initialization and subprocess exclusion. The current CI matrix passes both packaged startup checks. This validates the guarded X11 startup order under Xvfb, not native Wayland startup or interactive desktop behavior.

## Historical follow-up: Unix collector inputs

This pass originally covered Linux RAM input validation and Unix username lookup. Before changing the RAM parser, a temporary harness running the original parser confirmed that empty input returned `(0, 0)` and inconsistent cache counters caused subtraction overflow in a debug build.

- Linux RAM parsing now requires all six distinct counters with numeric values and `kB` units. Missing, duplicate, malformed, zero-total, or arithmetically inconsistent samples return an error. Checked arithmetic preserves the existing cache formula and the `total - free` fallback when unused memory exceeds total. The existing collector error path leaves RAM unavailable for that sample and retries on the next collection.
- Six RAM regressions cover valid accounting, field order and whitespace, missing/duplicate/malformed input, overflow/underflow, and successful reads after invalid or missing files.

The `getpwuid_r` hardening and its username tests were useful at the time, but PR #82 subsequently removed Unix username collection together with the unused user/UID transport fields. That deleted lookup has no remaining ABI, blocking-call, cache-recovery, or native macOS validation requirement. The RAM parser and its Linux filesystem-recovery tests remain current; its pure parsing tests also run on the other CI hosts.

No product or UX semantics were changed by the surviving RAM validation. Blocking filesystem reads remain subject to the collector-worker limitation described below.

## Native menu language synchronization

PR #79 changed only native menu synchronization. Re-running the original reactive block with a rejected native command confirmed that it recorded German as applied before the command completed and suppressed a subsequent German request. Preferences, locale persistence, system-language detection, and web translations retain their existing behavior.

The mounted frontend now owns a synchronizer and its locale-store subscription. Requested language and confirmed applied language are separate. One native call runs at a time; changes during that call coalesce to the latest selection. A successful reply records the language that actually completed, then reconciles any newer request. Failure invalidates confirmation because replacing a menu can partially mutate native state. Each new selection allows one initial attempt and two retries, delayed by 250 ms and 1 second. Duplicate requests do not reset that budget; a different active language or a fresh mount starts a new budget. Disposal unsubscribes and cancels retries, while an already dispatched native operation is allowed to finish.

The Unix command now builds and installs the menu inside a main-thread callback and awaits its result through a one-shot channel. This matters with the locked Tauri 2.11.5/Wry runtime: off-thread `set_menu` can enqueue native work before returning, whereas its nested main-thread operations execute inline when already on that thread. Dispatch success alone is not acknowledged as menu success. Build/replacement errors and a dropped callback are returned to the frontend. Windows retains its existing no-menu command behavior.

Ten frontend tests cover acknowledgement, automatic retry, exhaustion, latest-selection coalescing, stale failures/timers, switching back to a previous language, disposal, and immediate web translations through the real locale stores. Four Rust tests cover delayed acknowledgement, operation failure, dispatch failure, and a dropped callback. These tests are included in the current local and CI baselines above. PR #79 and the subsequent maintenance PRs passed all four build targets.

Native Linux/macOS menu rendering, translated About metadata, and unchanged menu actions/accelerators still require desktop testing. Test startup with a saved language, rapid switches through all four languages, and switching back while an update is pending. The completion result is the result reported by Tauri, not a visual verification: Tauri's menu internals do not propagate every lower-level GTK initialization error. No framework replacement or platform-specific menu implementation is included. A native operation that never completes is not timed out or overlapped with another non-cancellable update.

## Remaining manual and platform-specific validation

The build matrix is established and passing; it is no longer an outstanding validation item. The following gaps require interactive hardware, native desktop sessions, induced failures, or an authorized release scenario that the automated matrix does not provide:

1. On native builds, verify fresh samples arrive after startup; suspend/resume, adapter replacement, counter resets, and permission-denied process/sensor reads recover. A worker stuck in an OS read must leave the UI responsive and show stale status after five seconds. Quit must remain responsive.
2. On macOS, compare fallback CPU readings with `/bin/ps` and exercise empty, missing, and exiting PID sets. CI already runs the live-process fallback test on macOS. The deleted `kinfo_proc` bindings are not part of current validation.
3. On Linux X11/Wayland and on macOS/Windows, open/close preferences rapidly on either side of a screen, restart with preferences previously on the left, change DPI, unplug a monitor, and move to a short display. Confirm the main panel stays reachable, scrolling reaches all controls, and compositor refusals still allow preferences to open. Explicit position restoration remains compositor-dependent.
4. Verify production CSP permits Tauri IPC, appearance controls, local fonts, charts, and native external-IP lookup. In development verify HMR too. Mounted names containing HTML must remain text. CSP uses inline styles because the current components and charts need dynamic styling; scripts have no unsafe-inline/unsafe-eval allowance.
5. In an authorized release failure exercise, test a failed draft-build rerun, including replacing an already uploaded draft asset. The mocked regressions validate the rules, but not a deliberately failed live release. Confirm all nine expected bundles/checksum files exist before publication and downstream jobs run afterward. Published releases and old drafts without the source marker are deliberately refused; adopting such a draft requires explicit review, not an automatic provenance assumption.

For manual frontend testing, run `npm run dev` and open `/tests/browser.html?cpus=128&height=600`. This page uses Tauri's mock transport and never calls the external-IP service. It exposes `fixture.setMode("missing" | "rejected" | "stale" | "ready")`, `fixture.requests()`, and `fixture.stop()` in browser developer tools. Verify recovery, scrolling, escaped tooltip text, and no new polling after unmount. This supplements native testing; it does not simulate a compositor or WebKit/WebView2 IPC.

## Deliberately unchanged and remaining limits

- CPU normalization and load interpretation, which sensors constitute CPU temperature, sleeping-device zero-temperature aggregation, and whether disk throughput should measure whole devices or observed processes require product decisions.
- Interface inclusion, the four-disk limit, multiple-instance policy, and appearance storage policy remain unchanged.
- The CI and release matrix covers Ubuntu 22.04 x86_64, macOS arm64 and a Universal bundle, and Windows x64 with default features. It does not cover FreeBSD, non-default `battery`, `gpu`/`nvidia`, or `zfs` feature combinations, native macOS x86_64 execution, native Wayland sessions, or architectures outside those targets.
- macOS artifacts are ad-hoc signed but not notarized. Windows artifacts are not code-signed. Those are intentional release-policy limits, not uncompleted reliability validation.
- There is one collector worker. Rust cannot safely cancel an arbitrary blocked kernel or filesystem read; the UI remains usable, but telemetry cannot resume until that call returns. Independent collector workers or process isolation should be considered only with evidence of a recurring blocked source.
- The subprocess capture helper is scoped to trusted utilities such as `/bin/ps`. It does not promise process-tree cancellation for arbitrary shell commands whose descendants retain stdout.
- Dependency replacement and broad frontend modernization were not mixed into these correctness fixes. Subsequent maintenance PRs removed unused backend fields and inactive diagnostics without changing displayed behavior; regressions now assert the reduced transport shape. Release builds consume the existing npm/Cargo locks, but moving OS images and the repository's required stable Rust policy still limit bit-for-bit reproducibility.
